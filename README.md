## 为什么需要它

富士 X-T5 等机型在拍摄时会同时写入两个文件：

```
DSCF0001.RAF   85.5 MB   16 bit   — 原始传感器数据
DSCF0001.HIF   10.9 MB   10 bit   — 相机直出（含胶片模拟）
```

普通看图工具打开 RAF 时，往往直接显示文件**内嵌的 JPEG 预览图**。而那个预览图本质上就是相机直出的效果，与 HIF 几乎完全一样——实测两者仅 **4.5%** 的像素不同，拿来对照毫无意义。

本工具强制走 `kCGImageSourceCreateThumbnailFromImageAlways`，真正解码 RAW 数据（默认 Photoshop/Camera Raw 之外的系统级 RAW 渲染），与 HIF 的真实差异达 **92.5%** 的像素。

## 「解码 RAW」与「内嵌预览」的区别

这两个选项**只对 RAW 一侧有意义**（对 HIF / JPG 会被自动忽略，原因见下方「踩坑记录」）。

一个 RAF 文件里其实有**两份**图像数据：

```
DSCF0001.RAF
├── 传感器原始数据（Bayer 阵列，14 bit）   ← 「解码 RAW」读的是这个
└── 内嵌的整尺寸 JPEG 预览                ← 「内嵌预览」读的是这个
                                        （由相机自己的图像处理器生成）
```

| | 数据来源 | 谁来"显影" | 速度 |
|---|---|---|---|
| **解码 RAW** | 传感器原始数据 | macOS ImageIO 的通用 RAW 管线 | 较慢 |
| **内嵌预览** | 文件内嵌的 JPEG | **相机自己**（含胶片模拟、色调曲线、降噪） | 很快 |

关键差别在于**谁来显影**：

- **内嵌预览**是**相机**显影的结果，带着你设置的胶片模拟（Classic Chrome、Provia…）与全部机内处理；
- **解码 RAW**是**系统**显影的结果，ImageIO 走通用 RAW 管线，**不会套用富士的胶片模拟**。

而 HIF 直出同样是相机显影的产物。所以：

| 对比 | 平均差 | 差异像素 |
|---|---|---|
| RAF 内嵌预览 vs HIF | 0.80 | **4.5%** |
| RAF 解码 RAW vs HIF | 12.01 | **92.5%** |

内嵌预览与 HIF 几乎一模一样（都出自相机之手），真正解码的 RAW 才有九成以上像素不同。

**什么时候用哪个**

- **解码 RAW** —— 判断这张 RAW 的后期空间、看系统对原始数据的还原。默认模式，也是对照功能真正有价值的前提。
- **内嵌预览** —— 快速浏览相机原本的成像效果，或纯粹为了翻片快（解码快得多）。

## 右键菜单

在**中间栏的缩略图**或**第三栏的大图**上右键，两处菜单完全一致（共用 `PhotoContextMenu` 组件）：

| 菜单项 | 作用 |
|---|---|
| 拷贝图片 | 把图片本身放进剪贴板，可直接粘进聊天窗口 |
| 拷贝文件名 | 把这张的 RAF + HIF 文件名复制到剪贴板 |
| 在访达中显示 | 在访达里选中该照片的 RAF（没有则 HIF / JPG） |
| 添加到相册 | 用 Photos 框架加入「照片」App 的图库 |
| 移入废纸篓 | 把这张的文件移入废纸篓，受「删除前确认」开关约束 |

### 拷贝图片

写的是 **PNG 数据**而不是把文件本身放上去 —— 前者可以直接粘进聊天窗口，通用得多。

拷哪一份：**单图模式下拷当前显示的那一侧**（否则你看着 RAF 却拷到 HIF，而两者九成以上像素不同，会很意外）；其它模式优先 HIF。

长边**限制到 4096**（实测 4096×2731 / 14 MB）。全尺寸 7728×5152 有 4000 万像素，编码慢、粘贴目标多半还要再压一遍，不划算。编码放在后台线程，界面不会卡。

### 添加到相册

用 `PHAssetResourceCreationOptions` 的 **`shouldMoveFile = false`**（显式写出，绝不移动原片），并只申请 `.addOnly` 权限 —— 请求的权限越少越容易通过。

⚠️ **Info.plist 里必须有 `NSPhotoLibraryAddUsageDescription`**，否则一请求权限就被系统直接终止（不是报错，是崩）。`build.sh` 已加上。

⚠️ app 是 **ad-hoc 签名**，TCC 授权按二进制哈希记录 —— **每次重新构建后都需要重新授权一次**。

### 右键前的视觉反馈

SwiftUI 没有右键手势，`.contextMenu` 也不提供"即将打开"的回调，所以光看界面判断不出菜单要作用于哪一行 —— 而"当前选中"那行的蓝色高亮往往和菜单指向的行**不是同一行**，反而误导。

做法是**悬停高亮**：鼠标停在哪一行，哪一行就亮起来并露出一个垃圾桶图标。右键的那一刻，光标下那一行本身就是亮的，指向就明确了。

另外，**悬停别行时会把"选中"那行的高亮淡出**，避免两行同时亮着、反而分不清该删哪张。要实现这点，悬停状态得放在列表层（`ThumbnailGridView`）而不是每行自己存，否则各行不知道别处正被悬停。

**菜单作用于被右键的那一项** —— 列表里按下的是那一行，大图上按下的就是当前显示的那张。为此 `requestTrash` / `performTrash` 都增加了接收指定 `PhotoPair` 的重载，撤销栈、自动前进、列表更新等行为与键盘删除完全一致。

> 关于第三栏：画布是自绘的 `NSView`（`NSViewRepresentable`），本来担心 SwiftUI 的 `.contextMenu` 穿不透过去。用一个最小实验单独验证过——**能穿透**，所以两处用同一套 SwiftUI 写法即可，不必手写 `NSMenu`。

## 关于删除功能

挑片时按 `⌫` 即可，**RAF 与 HIF 会一起处理**，删完自动前进到下一张，方便连续挑片。

**撤销是多级的**：内部维护一个后进先出的撤销栈，每按一次 `⌘Z` 退回一次删除，可以一路连按把这一轮挑片删掉的都收回来。工具栏的撤销按钮会在还有多步时显示剩余步数，菜单里也会写明「还有 N 步」；栈空时菜单项自动置灰。栈上限 500 步。

删除后底部出现提示条，点「撤销」或按 `⌘Z` 即可恢复。

设计上是**进废纸篓，不是永久删除**，随时可以从 Finder 的废纸篓恢复。此外还有三道安全边界（见 `Sources/Trash.swift`）：

1. **只允许删除当前图库根目录之下的文件** —— 防止误操作波及其他目录；
2. **只允许删除已知图片扩展名**（raf / hif / heic / jpg / png / tif…），绝不碰其他文件；
3. **配对原子性** —— 一对文件要么全部成功，要么全部回滚，不会出现「只删掉 RAF、HIF 还在」的半残状态。

工具栏右侧的盾牌按钮可以开启**删除前确认**。默认关闭以获得最快的挑片速度，因为误删也能一键撤销。

> ⚠️ 注意：删除操作作用在**当前打开的目录**上。如果你把图库指向存储卡，删的就是卡上的原片（虽然也是进废纸篓）。挑片前建议先确认左上角显示的目录名是否正确。

**② 只是 arm64**，Intel Mac 跑不了；且需要 macOS 14+。

### 图标坐标的算法

窗口 660×520，两个主图标 y=200，说明文件 y=352。**位置不能随便填**：104px 的图标
加上下方标签，一个 item 从坐标点向上约占 52px、向下约占 72px。差 5px 就会让 Finder
**多出一条滚动条**（内容高 492，最下面的 item 下沿约 424，留足余量）。

### 背景图：两个坑

背景图由 `Tools/make-dmg-background.py` 生成（渐变底 + 蓝色箭头 + 文案）。

**箭头必须避开图标占位**，否则两端会被图标盖住：

| 元素 | 中心 x | 104px 图标的边缘 |
|---|---|---|
| App 图标 | 170 | 右边缘 ≈ 222 |
| Applications | 490 | 左边缘 ≈ 438 |

所以箭头只画在 **235…425** 之间。这个约束和 `make-dmg.sh` 里的 AppleScript 坐标是**耦合**的 —— 改图标位置就得同步改背景图。

**底色必须浅 —— 这是被骂出来的。**

Finder 渲染的**图标标签是纯黑的**（实测亮度 5–7），它**不会**因为背景图是深色就把标签变白。所以深色背景会让「`RAF-HIF 对照查看器.app`」这行字直接和背景融成一片：

| 背景 | 标签字色 | 标签处背景 | 差值 |
|---|---|---|---|
| 深灰（错） | 5–7 | 35 | **~30 → 看不见** |
| 浅色（对） | 36 | 239 | **203** |

我一开始只量了**自己画在背景图里的字**，一直觉得对比度没问题，完全没量 Finder 画的那行标签 —— 方向就错了。

所以现在是**浅底深字**：标题 `(24,24,30)`，副标题 `(78,78,90)`，底色 `(250,250,253)→(230,230,233)`。

**自检有三条**，跑 `Tools/make-dmg-background.py` 时都会打印：

1. 标称颜色的 WCAG 对比度（标题 17.0:1，副标题 7.9:1）
2. **渲染后**的实际最深亮度 —— 细笔画小字号经抗锯齿后会比标称暗一截（曾经标称 188 实测只有 130）
3. **Finder 黑色标签 vs 最暗处背景** 的对比度（16.4:1）—— 就是漏了这条才出的错

箭头另有一条自检：把箭头颜色像素与两个图标占位框求交，重叠必须为 0。

**① `.DS_Store` 会在卸载时被 Finder 覆盖。**

这是最反直觉的一处。实测数据：

| 阶段 | backgroundImageAlias | .DS_Store 大小 |
|---|---|---|
| 设置好时 | ✅ | 10244 字节 |
| `hdiutil detach` 后 | ❌ | **6148 字节** |

卸载时 Finder 把内存里的状态回写，**背景图设置被抹掉，图标坐标却留着**。所以
`hdiutil convert` 出来的成品永远没有背景图（试了 5 次，5 次全丢 —— 不是偶发）。

解法是绕开那次回写：

1. 可浏览挂载 → 设布局 → **立刻把好的 `.DS_Store` 存出来**
2. 卸载（会被 Finder 覆盖，无所谓）
3. 用 **`-nobrowse`** 再挂载（Finder 不接管）→ 把好的 `.DS_Store` 写回去 → 卸载
4. 转档，背景图就保住了

**② `hdiutil convert` 的 `-o` 目标已存在时会直接失败**，而 `set -e` 会让脚本静默退出，
重试根本没机会跑完。转换前必须先 `rm -f`。

> 另外注意：本机**没有** `/System/Library/Fonts/PingFang.ttc`。PIL 找不到字体时
> 会**静默退回默认位图字体**，结果是背景图里的中文全变方框且不报错。生成脚本里
> 用「两个不同汉字是否渲染成同一张图」来检测豆腐块，并逐个试候选字体。

## 已知设计要点与踩坑记录

- **「内嵌预览」只能用在 RAW 上。** 对 HEIF 使用 `kCGImageSourceCreateThumbnailFromImageIfAbsent` 时，ImageIO 会返回一个**没有像素数据的空壳 CGImage**——绘制出来完全透明，在深色画布上就是一片黑。修法有两层：① 先用 `UTType` 判断是不是 RAW，非 RAW 一律走完整解码；② 用 `isUsable()` 检查解出的图有没有像素数据，没有就退回完整解码。
- **布局尺寸必须放在非可观察的容器里。** 在 `GeometryReader` 中把尺寸回写给 `@Published` 属性会引发 AppKit 的约束更新死循环，直接崩溃（"more Update Constraints in Window passes than there are views"）。见 `LayoutBox`。
- **差异图不能用 `CIColorControls` 的 contrast 放大。** contrast 以 0.5 中灰为中心拉开，而差异值都贴近 0，提高对比度会把它们压成纯黑。必须用 `CIColorMatrix` 做线性增益。
- **解码精度按需分级。** 请求尺寸向上取整到 2 的幂作为缓存键（`ImageStore.bucket`），并按当前缩放级别决定解码精度，避免无谓地解 7728×5152 全尺寸。

## 滚轮翻页

光标停在画面上时，**不按 Ctrl 直接滚轮**即可上一张 / 下一张，方向与 PPT 一致（向下滚 = 下一张）。光标在列表或参数面板上时不影响它们自己的滚动。

鼠标滚轮与触控板的增量语义完全不同，分开处理：

- **传统滚轮**（`hasPreciseScrollingDeltas == false`）：一格就是一个事件 → **一格翻一张**，不受灵敏度设置影响；
- **平滑滚动设备**（`true`，含触控板与带平滑滚动的鼠标）：一次动作会拆成几十个小事件 → **累加到阈值才翻一张**，并忽略滑动结束后的惯性事件。

### 灵敏度可调（显示菜单 → 滚轮翻页灵敏度）

**不同鼠标上报的滚动增量差别极大**：传统滚轮一格是一个事件；而带平滑滚动的鼠标（苹果鼠标、部分罗技鼠标等）会像触控板一样上报一连串小增量 —— 两者相差可达一个数量级。同一个阈值不可能都对，所以做成了可调：

| 档位 | 阈值 |
|---|---|
| 慢 | 40 |

### 注意：平滑滚动类工具会改写滚轮事件

**Mos**（以及 SmoothScroll 等同类工具）的"**模拟触控板**"选项会把滚轮事件伪装成触控板事件发出来 —— 于是一个滚轮格被拆成十几个 `precise = YES` 的小事件，本工具就会误判设备类型，用触控板的累加逻辑去处理，结果"滚半天不动"。

排查这类问题的关键：**合成事件绕过这些工具**，所以我在本机怎么测都复现不出来（测出来永远是 `precise = YES`），只有真实设备的路径才会被改写。

遇到"滚轮翻页迟钝"时，先看 Mos 的「模拟触控板」是否开启；也可以直接用本工具的灵敏度开关适配。

累加值在 250 ms 无事件后重置（部分设备不上报 `phase`，只能靠时间间隔判断手势边界）；步进时是**减去阈值**而不是清零，大增量不会被吞掉。

> **验证范围说明**：合成出来的滚动事件**无论用 `.pixel` 还是 `.line` 单位，都被系统标记为 `precise = YES`**，因此「传统滚轮」那条路径无法用合成事件验证，只能靠逻辑保证（它不依赖任何阈值）。平滑滚动路径的阈值、方向、超时重置均已实测。

## 缩放

支持三种方式：触控板双指捏合、`Ctrl + 滚轮`、工具栏按钮。双指与 Ctrl+滚轮都**以光标位置为锚点** —— 缩放时光标下的那个点保持在原处，方便盯着细节看。

缩放范围按**实际像素比例**定义，而不是"相对适应窗口的倍数"：下限 2%、上限 1600%。这样原图再大、画布再小，都能缩放到 100% 以上做像素级检查。

锚点的几何算法抽成了纯函数 `CanvasNSView.anchoredPan`，并有专门的测试覆盖（25 种锚点 × 缩放组合，误差 < 0.01 图像像素）。

### 两个曾经算错的坑

**坑一：缩放倍率的基准取自视图而不是模型。**
`CanvasNSView` 里的 `zoom` 是 SwiftUI 传下来的副本，事件密集时会滞后。用它当基准算 `zoom × factor`，每轮都在用旧值，倍率被"吃掉"，缩放到一半就卡住（实测卡在 268%）。现在视图只上报**倍率**和**锚点**，真正的缩放值由 model 这个唯一权威计算。

**坑二：显示比例相对"解码后的尺寸"而不是"原图尺寸"。**
解码精度会随缩放变化（见下节），所以同一个缩放级别会读出不同的比例 —— 实测 `zoom = 1` 时，冷缓存读出 50%、复用高精度缓存读出 13%。这也让工具栏的「100% 像素」按钮**按错的比例走**，用户以为到了 1:1，其实没有。
现在 model 持有原图的像素尺寸（从 ImageIO 属性读取），显示比例一律相对它计算。修复后：适应窗口 13%、点「100% 像素」精确得到 100%。

## 显示保真度（HIF 与 Finder 是否一致）

**结论：一致。** 实测 app 实际画布渲染与 Finder 的 QuickLook 输出对比（同分辨率、色彩管理换算到 sRGB）：

| 照片 | 平均差 | 最大差 | 差异 >2 的像素 | 细节量 vs 参考 |
|---|---|---|---|---|
| DSCF0003 | 0.675 | 19 | 0.10% | 7.122 vs 7.116 |
| DSCF0001 | 0.750 | 3 | 0.00% | 1.149 vs 1.149 |
| DSCF0002 | 0.658 | 2 | 0.00% | 2.388 vs 2.383 |

剩下的零点几的平均差只是 10 bit → 8 bit 的取整。全分辨率下与「直接完整解码」逐比特相同（差 0.000），位深完整保留为 10 bpc。

### 两个曾经让画面变差的坑

**坑一：解码精度按「点」算，没乘屏幕倍率。**
Retina 上 900 pt 的画布实际有 1800 物理像素，却只解码 1024 px，等于硬放大 1.76 倍，画面明显发虚。现在按 `paneSize × backingScale` 计算。

**坑二：解码档位取 2 的幂。**
需要 1600 却解码 2048，画布还得再缩一次 —— 而**只要画布需要缩放，整幅图每个像素都会被重采样**。实测仅 3% 的过量（需要 1800 解 1856）就带来平均 4.3/255 的差异、细节量明显下降。现在档位按 8 px 粒度取整，基本等同精确尺寸，做到 1:1 直通、零多余重采样。

> 之所以敢用这么细的粒度：只有换片、缩放（去抖 320 ms）、画布尺寸变化（同样去抖）才会重新取档位，不会每帧都解码。

### 测量时要注意

画布缓冲用的是**屏幕的 ICC 色彩空间**（本机是显示器的 M27P20），而 QuickLook 输出是 sRGB。直接比原始 RGB 数值会把色彩管理换算误当成画质差异（实测会虚高到平均差 6–8）。必须先统一到同一色彩空间再比。

## 默认设置与按需解码

启动时默认是 **单图 + HIF**：HIF 只有约 10 MB，比 81 MB 的 RAF 小得多，适合快速浏览相机直出效果。

配套做了一件事：**按当前模式只解码需要的那一侧**。以前不管什么模式都会把 RAF 和 HIF 都解出来，单图模式下等于白白解一遍 81 MB 的 RAW。

| 场景 | 需读取 | 解码耗时 |
|---|---|---|
| 单图 + HIF | 10 MB | **68 ms** |
| 对照 / 闪烁（两侧都要） | 92 MB | 302 ms |

### 工具栏为什么要自适应

1. **视图模式与读取方式改成下拉菜单**，标签里直接显示当前值，占宽从 535 pt 降到约 200 pt；
2. **右侧控制组用 `ViewThatFits` 做三级降级**，保证任何宽度都不裁切：

## 本地化

界面语言**跟随系统设置**，支持简体中文与英文。

实现上有两个关键点：

**1. bundle 必须声明自己支持中文。** 否则 macOS 会把它当成纯英文 app，菜单栏的 File / Edit / View / Window / Help、标准菜单项、系统对话框按钮全都走英文。做法是在 `Contents/Resources` 放入 `zh-Hans.lproj` / `en.lproj`，并在 `Info.plist` 里声明 `CFBundleLocalizations` 与 `CFBundleDevelopmentRegion`。

**2. 采用「中文原文即 key」。** `Localizable.strings` 里写 `"对照" = "Compare";`。这样：

- `Text("对照")`、`Label("差异", …)`、`Button("取消")` 这类接受 `LocalizedStringKey` 的地方**不用改一行代码**，SwiftUI 自动查表；
- 万一漏翻某条，会**回落到 key 本身**（中文原文），不会显示出丑陋的键名。

需要显式调用 `L.t()` / `L.f()` 的只有三类：`String` 上下文（如 `Text(变量)`）、带插值的文案、以及赋值给模型的字符串。

改了文案后可以跑覆盖率检查，确认没有漏翻：

```bash
python3 - <<'EOF'
import re, os
CJK = re.compile(r'[\u4e00-\u9fff]')
LIT = re.compile(r'"((?:[^"\\\n]|\\.)*)"')
def strip_interp(s):
    out, i = [], 0
    while i < len(s):
        if s[i] == '\\' and i+1 < len(s) and s[i+1] == '(':
            d, j = 1, i+2
            while j < len(s) and d:
                if s[j] == '(': d += 1
                elif s[j] == ')': d -= 1
                j += 1
            out.append('%d'); i = j
        else:
            out.append(s[i]); i += 1
    return "".join(out)
def tbl(p):
    d = {}
    for l in open(p, encoding="utf-8"):
        l = l.strip()
        if not l or l.startswith(("/*","//")): continue
        m = re.match(r'^"((?:[^"\\]|\\.)*)"\s*=\s*"((?:[^"\\]|\\.)*)"\s*;', l)
        if m: d[m.group(1)] = m.group(2)
    return d
en = tbl("Resources/en.lproj/Localizable.strings")
zh = tbl("Resources/zh-Hans.lproj/Localizable.strings")
used = set()
for fn in os.listdir("Sources"):
    if not fn.endswith(".swift"): continue
    for line in open(f"Sources/{fn}", encoding="utf-8"):
        if line.strip().startswith("//"): continue
        for m in LIT.finditer(line.split("//")[0]):
            s = m.group(1); f = strip_interp(s)
            if CJK.search(s) or f in en: used.add(f)
print("缺英文:", sorted(k for k in used if k not in en) or "无 ✅")
print("缺中文:", sorted(k for k in used if k not in zh) or "无 ✅")
print("死条目:", sorted(k for k in en if k not in used) or "无 ✅")
EOF
```
